# Delegation and specialist routing

Version: 1.1. Roles are instruction profiles, not independent permission boundaries.

## Discovery before routing

Enumerate available subagent tools and project/user agent definitions permitted by current scope. Inspect matching description and relevant instructions; don't read unrelated histories or credentials. Qualify only the capabilities needed for the assignment; reuse unchanged qualified runner/toolchain/profile evidence, refreshing affected dependencies or availability when it changes. Record identity, invocation method, scope and evidence proportionately; no repeated full census for an unchanged procedure. Matching names alone do not prove capability. Never overwrite or rename an existing REA profile.

REA means Reverse Engineer Anything as named by this user. Discover current REA roles/tools in the session catalog rather than treating an old installation snapshot as current availability. Advertised tools establish exposure, not server health or permission for an operation. Qualify identity and the bounded capability needed for this task before use; do not run setup, analysis or process operations merely to claim readiness. If unavailable, use simoder-researcher for bounded source/ABI investigation and explicitly disclose the fallback; don't claim it is REA or has disassembly tools.

## Dispatch

Use an existing verified specialist when it fits the goal better than a generic worker. Use [the handoff contract](contracts.md): an ordinary message with goal, ownership, evidence and next action; include applicable constraints, exact binary identities and stop conditions when relevant. No mandatory handoff file or microplan. For REA ask for concrete binary identity, offsets/RVAs, calling convention, ownership/thread/lifetime, signature checks and counterevidence. A returned hypothesis cannot authorize patching a game process.

If the host supports custom role selection, select the verified role name. If spawn API accepts only a task/prompt, spawn with inherited model and explicitly instruct it to read the matching role file. Do not invent role/model parameters. Do not create user-visible chats for internal work. No recursive spawning by children unless separately delegated in task scope.

## Ownership and integration

Coordinator owns global scope and integration; workers own disjoint file sets. Auditors do not modify implementation. Reserve game/session/region/ports and shared services; one writer per resource, version preconditions and explicit conflict resolution. Parallel read-only analysis is allowed; concurrent edits to the same files aren't. A resource reservation is procedural until a lock implementation is verified.

Receiving agent rechecks actual baseline, grants and tools. Stop on overlap, unknown game context or unsupported ABI. Report evidence, confidence, blockers and next safe action. Coordinator reads actual artifacts, reconciles dependencies and validates the combined result. Separate subagent review improves independence of reasoning, not OS/process isolation; distinguish from required human acceptance.


One independent nonauthor may cover all applicable stage audit scopes; add experts only when needed. Keep one living stage STATUS/decisions and final REPORT/audit, not repeated records per delegate or fix.
