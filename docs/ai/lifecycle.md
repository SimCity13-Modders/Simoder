# Lifecycle and gates

Version: 1.1.

1. Establish the requested outcome, exact repositories/paths, current authorization and baseline content including relevant dirty/untracked work. Apply SAFE_ADD: preserve existing work; resolve overlapping dirty scope before edits unless the user explicitly authorizes its disposition or isolated additions. Read targeted policy/knowledge.
2. Agree the LARGE stage (for example U4/U5), risk and measurable criteria. Use one living STATUS/decisions record under .analysis/<stage>/; smaller labels remain task/test IDs. A stage must not become an umbrella for unapproved scope. New architecture, material contracts/dependencies, security policy, privilege expansion, destructive or external actions and other new risk require independent pre-review and applicable explicit approval before effects. Ordinary fixes within approved scope do not reopen settled approval.
3. Implement large coherent vertical batches with clear module/file ownership, complete behavior, Doxygen documentation and relevant public API/architecture/user docs. Ordinary handoffs may be messages. Compile early and run targeted regression/failure/recovery checks in the approved local disposable workspace BEFORE independent implementation audit; no separate pre-audit of routine source/type/test fixes merely to execute the same approved local procedure.
4. Reuse the stable audited runner, toolchain, security profile and input namespace. A new run ID, source input or ordinary internal fix does not require a new procedure/report/full SDK or repository census when effect scope, commands, ownership and security profile are unchanged. Record exact executed source/image identities and raw results for every run; refresh affected dependency evidence when it changes. Before new risks, independently review the actual effect delta and obtain applicable approval. Never force-kill/replay ambiguous live originals, delete unknown paths, relax tests or bypass guards.
5. Collect all independent required cases in one batch where safe; any required failure leaves the overall result FAIL. Preserve failed raw logs grouped under the stage, actual coverage and NOT_RUN; never erase history to fit the current report. Builds and fixtures do not establish game/client/release acceptance.
6. At the LARGE stage boundary, one independent nonauthor may cover all applicable audit scopes; use extra experts only when needed for competence, conflict or risk. Protected instruction changes require independent security and knowledge validation. Audit actual source/diff/tests/integration, not only the report. Re-audit substantive fixes and affected integration against results; reuse unchanged evidence. Do not audit every informational manifest/report edit.
7. L2/L3 stage completion requires explicit human acceptance of the final audit and exact reviewed content. No self-issued signatures/tokens. Consolidate only task-owned unpublished checkpoints after acceptance, verify identical content and rebind evidence. Changed material content repeats affected audit and acceptance. Preserve published/other-owned history. Push/publication/release remain separate authorization.

Maintain one current final REPORT and finding registry; update them without multiplying numbered audit versions or verbose human records per function/fix/commit. Preserve prior evidence/history. Records scale to risk; ordinary small work needs no mandatory microplan, dossier or new handoff file. Required public documentation still changes normally.

COMPLETED requires all applicable criteria and gates; otherwise report PARTIAL/BLOCKED/REJECTED/CANCELLED. Separate implementation, verification, human acceptance and release status. PASS/FAIL/BLOCKED/NOT_RUN describe actual checks only. On resumption recheck relevant state, permissions and evidence freshness. Bounded retries require cause; observe ambiguous side-effect outcomes before retrying.
